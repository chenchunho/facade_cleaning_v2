## 0. 這件事真正的難點

per user 已拍板**最終走有線**。但今天的鏈路狀態是：

| 條件 | 隧道 `192.168.1.10` | WiFi `192.168.5.25` |
|---|---|---|
| 閒置 ping（本體實測，09-09） | avg **306ms** / max **568ms** / 0% | **8.5ms** / 0% |
| 閒置最大空窗（09-08） | **903ms** | — |
| **VFD 運轉**（09-08 受控實驗） | **90% 丟包**，roll age 758 → **7,206ms** | **0% 丟包** |

而 IMU 推送是 **4Hz（`IMU_PUSH_PERIOD_MS = 250`）**、時效門檻 **`IMU_ROLL_STALE_MS = 750`（3 tick）**。

⇒ 🔴 **即使閒置，隧道的 903ms 空窗就已經破門檻**；而 `cycle_test` 的步驟 ⑦ 是
`crane pay_out 40`（VFD 運轉）—— **正好是隧道掉 90% 的那個時刻**。
**現在直接切過去跑，整段下降的平衡會全程退回 `src=meter`，測到的不是我們以為的東西。**

**所以順序不能倒過來：電氣 → 門檻 → 切換 → 測試。**

## 🔴 三個會讓這個計畫失效的點（先看這個）

### ① `cycle_test.py` 自己就吃 WiFi —— 不改它，「切到有線」是假的

```python
CRANE  = ("127.0.0.1", 5002)      # 腳本跑在吊機上
WROBOT = ("192.168.5.26", 5001)   # 🔴 透過 WiFi 指揮本體
```

⇒ 就算把「本體→吊機」切到隧道，**測試指令本身仍走 WiFi**。
要真的驗證有線鏈路，`WROBOT` 必須改成 **`192.168.1.100`**（本體 eth0）。
📌 **不改也可以，但那時要誠實說「這輪只驗了本體→吊機那一段」**，不能宣稱驗過有線。

### ② 兩個方向都沒有背景存活偵測（09-09 查出）

10 週期是**長時間、大半無人盯著**的測試，而現在：
- 吊機端 watchdog 心跳走 loopback ⇒ 結構上偵測不到網路故障
- 本體端的吊機 watchdog 是**死碼**（`crane_last_ok_ms_` 0 處讀取）
- `crane_keepalive` 自 2026-05-15 起未啟動

⇒ **鏈路在測試中途掉了，沒有任何背景機制會發現。** 在一條已知脆弱的鏈路上跑長測，
這是最不該缺的東西。**建議至少先做「觀測」那一版**（見 Phase 2.3）。

### ③ 門檻不要用猜的

`IMU_ROLL_STALE_MS` 的新值必須來自 Phase 1 的**實測分布**（p99 / max gap），不是拍腦袋。
📌 09-08 的教訓：先調門檻＝**把一條在運動時 90% 死掉的鏈路用更寬的門檻蓋起來**。

## Phase 1 — 電氣處置（🔴 需 per user 現場，我只負責量）

### 1.1 一次只改一個變因

依 09-08 的排序，**最強候選是供電耦合**（HomePlug 靠訊噪比工作，電源軌被污染直接殺 SNR）：

1. **吊機端 Fathom-X 改獨立電源（電池）** ← 最便宜的決定性測試
2. 沒改善再看：板子實體位置（是否貼著變頻器／動力線）／線材是否與動力線同束

⚠️ **不要同時改兩項**，否則分不出是哪一個。

### 1.2 量測（我執行）

```
# 在本體 .26 上
./link_probe.sh preflight                 # 先確認兩條路徑都不是冷的
./link_probe.sh run 420                   # 5Hz / 420s，中途 per user 按住 ▲ 拉繩一次
./link_probe.sh analyze <前綴> <HOLD起> <HOLD迄>
```
HOLD 窗口取自吊機 log 的 `HOLD-TRACE`；`offset` 在操作端先跑（09-09 實測偏移 +0.522s）。

### 🚦 Gate 1 —— 通過才進 Phase 2

| 判準 | 門檻 | 為什麼 |
|---|---|---|
| HOLD 期間隧道**最長空窗** | **< 750ms** | 直接對上 `IMU_ROLL_STALE_MS`，不用改門檻就能用 |
| 同上，退一步 | **< 1,500ms** | 可用，但要調門檻（Phase 2） |
| WiFi 同窗對照 | 仍 ~0% | 確認是隧道改善不是整體變好 |
| 閒置最長空窗 | **< 750ms**（09-08 是 903ms） | 閒置就破門檻的話，運動時不可能好 |

🔴 **空窗 > 1,500ms ⇒ 電氣沒解決，停在這裡，不要往下走。**
（那代表隧道仍不能當控制鏈路，硬切只會把問題搬到測試裡。）

## Phase 2 — 定門檻（資料驅動）

### 2.1 `IMU_ROLL_STALE_MS`
用 Phase 1 的實測分布定：**取 p99 空窗 × 1.5，向上取整到 250ms 的倍數**（對齊 tick）。
🔴 **同時記錄「這個值是在什麼條件下量的」** —— 09-08 的教訓是 WiFi 上量不出這個缺陷。

### 2.2 是否提高 IMU 推送頻率
`IMU_PUSH_PERIOD_MS = 250` ⇒ 掉 3 個封包就過期。提高頻率能換到餘裕，代價是隧道流量。
**Gate 1 若只是勉強過，這個比放寬門檻更值得做**（放寬門檻是降低偵測力，提高頻率不是）。

### 2.3 🔴 強烈建議：先補上「鏈路可見度」再跑長測
最低成本版本（AI-2 建議、我同意，**不新增任何流量**）：
`imu_push_loop_` 已經每 250ms 在讀那條 socket 卻直接丟掉 ⇒ 改成
① 丟給 `handle_crane_evt_`（吊機的警報終於送得到本體）
② 連續失敗計數曝露到 `cmd_status` 的 `peer_age_ms`
⇒ **它是 hold／長測期間唯一還在跑的本體→吊機流量，現成的鏈路探針，只差沒人記分。**
📌 這也正好給出 Phase 2.1 需要的「鏈路實際斷多久」那個數字。

### 🚦 Gate 2
門檻已定且有實測依據；`peer_age_ms` 看得到（若採 2.3）。

## 🔎 補記（09-09）：「10 次」有**兩支**腳本，是不同的東西

per user 提示後實查。**兩支在 repo 與吊機上都逐位元一致**（`cycle_test.py` 50,359 B md5 `374498616c35`／
`mission_run.py` 10,293 B md5 `adcef8d0df9a`）——**沒有衍生副本過期問題**，這次是乾淨的。

| 腳本 | 一輪是什麼 | 中止門檻 | 性質 |
|---|---|---|---|
| **`cycle_test.py 10 5 40`** | 10 週期 × 下降 5 步 × 40cm，**每步含完整清潔動作**（真空腳→推桿→DEPLOY_F 力控壓上 15 N·m→滑台 0→100→0→收手臂→風扇），到底 50Hz 拉回 | roll **6.0** / diff **8.0**，各需連續 3 筆 | **大的那個**，全機構耐久 |
| **`mission_run.py 10`** | 地面↔頂端 **10 趟來回（20 次橫越）**，只有吊機行走 + 姿態監看 | roll **5.0** / diff 8.0 **＋ `tension_valid=0` 立即停** | 純行走的統計樣本 |

⚠️ 兩支的 `WROBOT` **都是** `("192.168.5.26", 5001)` ⇒ 上面 🔴① 那條對兩支都成立。

### 🟢 建議順序：`mission_run.py 10` → `cycle_test.py 10 5 40`

理由**不是**它比較短：

1. **純吊機行走 ＝ VFD 全程在轉 ＝ 對隧道最兇** —— 而隧道正是這次要驗的東西
2. **沒有推桿／風扇／真空** ⇒ 混淆項最少。09-02 兩次中止（`extend_raw TIMEOUT`、
   `pwm_freq_write_failed`）都來自這三者，跟鏈路無關卻會把一輪測試報銷
3. 隧道若撐不住，**在這裡就現形**，不必先賠上一輪完整週期測試

📌 **它也直接對應 09-01 立下的理由**：`mission_run` 當初就是為了「趟與趟之間的變異與被比較的效果一樣大」
而生的 —— 20 次橫越本身就是統計樣本。拿它當鏈路驗收，等於同時拿到姿態基準線。
