## 0. 系統邊界(總綱,per user 2026-09-13)

> 🎯 **吊機與本體兩個電控箱之間只共用兩樣東西:① 同一組單相 220V 進線、② 隧道(2-wire tether / HomePlug)通訊。
> 其餘 —— 24V、5V、RS485 各段、繼電器、感測 —— 全部各自電控箱負責,互不牽連。**
>
> 這條邊界**與軟體邊界完全對齊**(`SOFTWARE.md` §1:吊機程式跑吊機 Pi、本體程式跑本體 Pi,只靠 TCP 行協定講話):
> - 判斷任何事件的波及範圍,先問它是「220V 側」還是「隧道側」還是「箱內」——
>   **箱內事件(如本體 24V blip)不會跨箱**;**220V 側事件同時打兩箱**;**隧道側事件只斷通訊、不斷電**。
> - 日後任何「讓一箱的電/訊號接到另一箱」的改動(例如共用 24V、把感測器拉過隧道),都是在**打破這條邊界**,
>   要先回來改本節與 `SOFTWARE.md` 的責任劃分。

## 2. 網路拓樸

```
 外部(頂樓/地面)                                         機身 / 頂樓
   ──2-wire tether(HomePlug AV)──► Fathom-X Tether Board ──Ethernet──► 8-Port PoE Switch
                                                                            │
                        ┌──────────────────┬────────────────────────────────┼──────────────┐
                    本體 Pi5            吊機 Pi                      6× USR-TCP232-304    X518(原生 TCP)
                    192.168.1.100       192.168.1.10                 (RS485↔TCP 透明傳輸)  192.168.1.33:502
                    WiFi 192.168.5.26   WiFi 192.168.5.25            .20 .21 .22(本體)
                                                                     .30 .31 .34(吊機) + .32 ZS-DIO
```

- 🔴 **HomePlug AV(2–30 MHz)與 VFD 噪訊同頻帶**:2026-09-08 受控實驗 VFD 一運轉該鏈路掉 **90%** 封包
  (同一秒 WiFi 90/90 全通)。⇒ **目前上機測試暫全走 WiFi**(`SOFTWARE.md` §1.3),有線是既定終點但物理層要先解(隔離/濾波,見 `plans/wired_switch_and_loop_test_plan.md`)。
- 網關全為 USR-TCP232-304,**透明傳輸**(非 Modbus 閘道):回覆會被切成多個 TCP 段、每台最多 4 條 TCP 連線、半雙工序列化 —— 三個結構性問題見 `reference/comms_interface_for_pcb.md` §4。
- **交換器**:吊機 = **8-port PoE Switch**、本體 = **5-port hub**(per user 2026-09-13);兩端各一片 Fathom-X 載波,**各吃本箱 24V**。
- **本體與吊機各自獨立電控箱**(5V 電源分開,見 §5)。**RS485 主匯流排網關 6 台**(USR-TCP232-304):本體 3(.20/.21/.22)、吊機 3(.30/.31/.34);另有水閥網關 `.32`(ZS-DIO/USR_W,2026-09-10 加)與 X518 張力(原生 TCP `.33`)。
- 主機端點可用 `FCV_EP_<NAME>_HOST/PORT` 執行期覆寫(`common/endpoints.h`)。

這解釋了 blip 為何看起來「通訊也掛了」—— 不是巧合,是同一顆電源;也表示 **blip 當下沒有任何有線路徑能送急停**(WiFi 是另一條)。
**對策方向**:① 量 24V 實際總負載與堵轉峰值 ② **把手臂 M1/M2(及/或幫浦)分離到獨立電源**,或加大 24V 供電
③ 加斷路/限流保護 ④ 軟體側已降力 8 Nm 緩解(治標)。

### 5.1 🔴 無過流保護(2026-09-12 per user 確認:**斷路器/保險絲都沒裝**)

**全系統沒有任何外加過流保護** —— 兩個電控箱都沒有斷路器,也沒有保險絲。這件事把 §5 的 blip 圖像補完了:

- **唯一在動作的「保護」是電源供應器自己的過載保護。** LRS-150-24 屬 Meanwell LRS 系列,
  該系列的 OLP 是**定電流限流 + 故障排除後自動恢復**(hiccup)。
  🎯 **這正好解釋 blip 的波形** —— 電壓垂降然後**自己回來**,不需要有人去復歸:
  那不是接線故障,是 **PSU 進入自己的過載保護再自動恢復**。
  ⚠️ **此為強假說,尚未核對 LRS-150-24 手冊的 OLP 條件(105–135% 額定)與恢復行為** → 列入待查。
- **後果**:① 過載時沒有任何選擇性 —— 垂降的是**整條 24V bus**,所以繼電器、幫浦、ZDT 計數器
  **一起掉**(現象吻合);② 真的發生短路時,沒有東西會先跳,只能靠 PSU 自保或線材燒斷;
  ③ 220V AC 側同樣沒有保護,而這台機器**帶水作業** —— 與待辦總表「漏電保護(RCD)為必要非選配」
  那條 🔴(2026-09-01 per user 暫緩)是同一個缺口。
- 📌 **這改變了 24V 治本的選項排序**:原本只想「分離供電 or 換大 PSU」,
  但**加裝過流保護是獨立且更便宜的一刀**,而且它處理的是「短路」這個目前完全沒防的情境
  (換大 PSU 反而讓可用故障電流變大)。三者可並行評估。

**待現場確認**:24V 實際總負載與峰值;**LRS-150-24 手冊的 OLP/hiccup 行為**(驗證上述假說);MH300 中繩絞盤供電。

#### 🔴 螺旋槳單路 PWM 的三個後果(2026-09-12 確認後補)

1. **結構上無法差動** —— 兩槳永遠同轉速。任何「靠左右推力差修正姿態/偏擺」的想法**在現行硬體下不成立**,
   不是軟體沒寫。(程式只寫一路 `PWM_STEP_CH=1` 是**正確的**,不是漏寫。)
2. **單邊失效無法偵測、也無法補償** —— 一顆 ESC/馬達/NPP 掛掉時,另一顆**仍收到相同 duty 繼續全推**,
   產生淨力矩使機體繞鋼索偏轉;系統**沒有任何回授**知道這件事(無轉速/電流回讀)。
   ⇒ 待辦總表「單邊推力失效」那條的處置**只能走硬體**(例如兩顆 NPP 的 DC OK 訊號進 DI 做互鎖),
   **軟體差動補償這條路是死的**,不要再往那個方向提。
3. **單點失效會同時帶走兩具** —— 一條 PWM 訊號線 + `斷線維持輸出` 的組合:訊號線斷掉時,
   兩具螺旋槳**一起卡在最後的 duty 持續運轉**,而且是同時。急停必須能**切斷 57.6V 動力**,
   光靠送 PWM=停止值是不夠的(送不到)。
