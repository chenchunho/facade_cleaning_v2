# harness — 重構的等價性驗證（不需要機器）

> 建於 2026-08-29，服務 `.claude/refactor_plan.md` 階段 0。
> **目的只有一個**：證明重構之後，程式對外的行為沒有變。

## 判準

這支程式對外的契約就兩樣東西：**匯流排上的位元組**、**TCP 回的文字**。
兩樣都一樣，重構就是正確的 —— 定義上如此，不需要靠人判斷。

| # | 判準 | 性質 |
|---|---|---|
| 1 | **TCP 文字回覆**（`replies.txt`） | 完全確定性，由指令腳本逐條驅動 |
| 2 | **分裝置的位元組序列**（`trace.norm`） | 每個 `[DEV:ID]` 各自比對 |

🔴 **判準 2 為什麼要分裝置**：主程式有多條背景執行緒（`crane_wd_thread_` /
`crane_keepalive_thread_` / `imu_mon_thread_` / 吊機的 `meter_loop`、`hold_loop`、
`vfd_keepalive_loop`）各自寫 stderr，**全域行序是排程器決定的**，同一支程式跑兩次就不同。
直接 diff 整份軌跡會滿江紅，而且每一條紅都是假的。

⚠️ **這個取捨的代價**：如果重構改變了「先跟哪個裝置說話」的**順序**，判準 2 抓不到。
那一半靠判準 1 守（它是確定性的，而且是程式的功能輸出）。

## 用法

```bash
sudo apt install -y g++          # 只需一次；本機目前沒有
./harness/negative_control.sh    # 🔴 先跑這個
./harness/compare.sh main-final HEAD
```

## 🔴 先跑負控制，再相信任何綠燈

`negative_control.sh` 會故意把一個常數改壞（`ZDT_RF2` 7→8），確認 diff 會紅。

**沒有紅過的綠燈不算綠燈。** 2026-08-29 的實例：
`Linux_test/fake_slaves/test_qx_do24.cpp` 的斷言寫反了
（`if (init(...)) FATAL`，而 `QX_DO24::init()` 是 `true`=成功），
**一個斷言都沒跑到卻回報通過** —— 那支測試從寫出來到當天從沒真正跑起來過。

同一天在寫這個 harness 時又踩了一次同型的坑：測 `normalize.py` 的時候，
比對兩份時間戳不同的資料「相等 ✅」，**實際上兩邊都解析失敗、都是空字串**。
→ **所以每個比較之前都要先斷言「解析到的筆數 > 0」。**（`normalize.py` 空輸入回 exit 2。）

## 檔案

| 檔案 | 用途 |
|---|---|
| `fake_bus.py` | 假的 USR 網關，一台服務整條 bus 的所有 slave。RTU-over-TCP 與 MBAP 兩種 |
| `build.sh` | 本機 x86-64 建置。兩種目錄佈局都支援（`main-final` 沒有 `app/`／`common/`） |
| `run_trace.sh` | 起假匯流排 → 跑主程式 → 灌指令 → 收軌跡與回覆 |
| `normalize.py` | 剝時間戳、只留 hex dump、依裝置分組 |
| `compare.sh` | 兩個 commit 各建各跑，兩個判準都比 |
| `negative_control.sh` | 注入缺陷，證明工具會紅 |
| `cmds/*.txt` | 指令腳本 |

## 🔴 這套東西證明不了什麼

- **證明不了功能正確**，只證明兩個版本**行為相同**。功能正確要靠實機（`runbook.md` §A2）
- **證明不了腳本沒碰到的路徑**。覆蓋率是最弱的一環 —— `cmds/*.txt` 沒送到的指令，
  相關的重構改動不會出現在軌跡裡，**而 diff 依然是綠的**
- **假從站的值是合理的假值，不是真值**。目的是讓兩個版本走過同一條路徑，不是模擬機器

## 與 `Linux_test/fake_slaves/` 的分工

| | 服務對象 | 送好幀還壞幀 | 目的 |
|---|---|---|---|
| `Linux_test/fake_slaves/` | 單一 slave | **故意送壞幀** | 驗 driver 的回覆驗證路徑 |
| `harness/` | 整條 bus 的所有 slave | **永遠送好幀** | 讓主程式跑起來產生可比對的軌跡 |

兩者互補，不要合併。

## 設計約束（改這裡的東西之前先讀）

1. **假從站的回覆必須是請求的確定性函式** —— 不用亂數、不用時鐘、不保存跨請求狀態。
   任何一點隨機性都會讓兩次執行分岔，而那個分岔**看起來會跟重構搬壞一模一樣**。
2. **廣播（slave `0x00`）必須什麼都不回** —— ZDT `trigger_sync_move` 的正確性
   建立在「廣播沒有回覆」上；假從站若禮貌地回一個 ack，就會把那條路徑測成錯的。
3. **`ep::*` 沒設環境變數時行為必須逐位元不變** —— 用來做等價量測的東西，
   自己不能擾動被量的對象。
4. **等埠開了才往下走，不要用 `sleep` 猜** —— 間歇性失敗會讓人開始不信任綠燈，
   而一套沒人信的驗證等於沒有。
